# 项目宪章（Constitution）

> 本文件是本项目**最高级别的约束文档**，约束所有 Agent（含编排 Agent、各领域 Agent、代码生成 Agent）在生成 **规格文档、UML、代码、测试** 时的行为。
> 本宪章与 `00-project-brief.md`、`01-clarifying-questions.md` 共同构成约束体系：**简报定义"做什么"，澄清记录定义"未定什么"，宪章定义"怎么做、不能怎么做"。**

| 项 | 内容 |
|---|---|
| 文档编号 | `specs/constitution.md` |
| 文档类型 | 工程约束 / Agent 行为规范 |
| 版本 | v1.0 |
| 状态 | ☐ 待人工审查（审查通过后对所有 Agent 生效） |

| 适用范围 | 本仓库 `specs/` 下所有规格、`backend/` 下所有代码与测试、所有 UML 制品、所有 Agent 会话 |

## 0. 如何使用本宪章

1. **Agent 在开工前必须完整读取本文件**，并在生成任何制品前逐条自检（见 §14 自检清单）。
2. 每个原则包含：**声明** / **具体要求** / **禁止事项** / **验收检查** 四部分。
3. 原则编号为 `P-01` ~ `P-11`，在评审、审查记录、AI 使用日志中**一律引用编号**，不得改写为自然语言描述。
4. 违反原则的产出物**一律视为无效**，必须回滚并由人类决定处置方式（见 §12 违规处置）。

## 2. P-01 · Specs 优先原则（Spec-First）

### 声明
**任何代码实现之前，必须先完成完整的规格文档链。** 不允许"边写代码边补文档"，更不允许"先写代码再倒推文档"。

### 具体要求
1. 进入编码前，`specs/` 下必须存在并通过审查的文档（编号以 `00-project-brief.md` §10 路线为准）：
   - `00-project-brief.md`（已基线）
   - `01-clarifying-questions.md`（人类回答已录入）
   - `02-use-cases.md`（需求与用例规约）
   - `03-domain-model.md`（领域模型 / 类图）
   - `04-business-rules.md`（业务规则）
   - `05-architecture.md`（架构设计）
   - `06-database-design.md`（数据库设计）
   - `07-api-spec.md`（接口规格）
   - `08-test-plan.md`（测试计划与用例）
   - `09-tasks.md`（任务拆解，逐条可勾选、可追溯至用例编号）
2. 任务拆解（`09-tasks.md`）中的每一项必须能追溯到一个用例编号（UC-xx）或一条业务规则编号。
3. 编码顺序必须遵循 `09-tasks.md` 的排列，**不得跳序实现尚未规格化的功能**。

### 禁止事项
- 禁止在缺规格的情况下"先跑通再说"。
- 禁止用代码注释替代规格文档。
- 禁止在实现过程中"顺手"添加规格中不存在的功能（范围蔓延）。

### 验收检查
- [ ] `specs/` 下 10 份文档齐备且状态为"已审查"
- [ ] `09-tasks.md` 每项均带 UC / 规则编号
- [ ] `backend/` 首次提交的代码均可追溯到某条任务项

## 3. P-02 · Agent 起草，人类确认原则（Agent-Drafts, Human-Approves）

### 声明
**所有由 Agent 生成的规格、UML、设计、代码、测试，在经人工书面确认前，一律只是"草案"，不得作为实现依据，不得合并入基线。**

### 具体要求
1. 每份 Agent 生成的文档必须在文件头标注：

   ```
   | 生成方式 | Agent 起草（模型：____） |
   | 审查状态 | ☐ 待人工审查 / ☑ 已人工确认（确认人：____，日期：____） |
   ```

2. Agent 产出后必须**主动列出需要人类确认的要点清单**（假设、取值、取舍），不得静默交付。
3. 人类确认的最小颗粒度为**单份文档**；一份文档未确认，不影响其他已确认文档，但**依赖它的下游文档不得定稿**。
4. 人类修改意见被采纳后，Agent 必须重新生成受影响部分并**再次提交审查**，不得只改局部不更新版本号。

### 禁止事项
- 禁止将"用户没有反对"默认为"已确认"。
- 禁止在文档状态仍为"待审查"时引用其结论去生成下游制品。
- 禁止由 Agent 自行修改"审查状态"字段。

### 验收检查
- [ ] 每份规格文件头含生成方式与审查状态
- [ ] 每份文档附有"待人类确认要点清单"
- [ ] 下游文档所依赖的上游文档均为"已人工确认"

## 4. P-03 · UML-as-Spec 原则

### 声明
**UML 图不是文档的装饰插图，而是规格本身的一部分。** 图与文字规格具有同等效力；二者冲突时视为**规格缺陷**，必须人工裁决，不得由 Agent 自行取舍。

### 具体要求
1. **必须使用文本化格式**（PlantUML `.puml` 或 Mermaid `.mmd`）保存，纳入版本管理，禁止上传不可 diff 的二进制图片作为唯一来源。
2. 必须产出的图（最低集合）：
   | 图类型 | 对应文档 | 说明 |
   |---|---|---|
   | 用例图 | `02-use-cases.md` | 参与者 A-01~A-05 与 UC-01~UC-11 关系 |
   | 类图（领域模型） | `03-domain-model.md` | 读者类型、借出物类型、标题/副本、借阅记录、预约、罚款 |
   | 包图 / 组件图 | `05-architecture.md` | 四层依赖关系 |
   | 顺序图 | `05-architecture.md` 或 `02-use-cases.md` | 至少覆盖：借书、还书（含罚款）、预约、超期判定 |
   | 状态图 | `04-business-rules.md` | 借阅记录状态、预约状态、借阅证状态 |
3. 图中的**类名、属性名、方法名、关系基数**必须与 `06-database-design.md` 和 `07-api-spec.md` 严格一致。
4. 文本图源文件统一存放于 `specs/diagrams/`，文档中通过相对路径引用。

### 禁止事项
- 禁止只贴图片不提供文本源。
- 禁止图与文字规格各说各话。
- 禁止在类图中使用与数据库表、接口字段不一致的命名。

### 验收检查
- [ ] `specs/diagrams/` 下存在用例图、类图、包图、顺序图、状态图的文本源
- [ ] 图内命名与 `06` / `07` 文档交叉核对一致

## 5. P-04 · Baseline 原则

### 声明
**规格一旦通过人工审查即建立基线（Baseline）。实现阶段，Agent 不得擅自修改 `specs/` 下的基线文档。**

### 具体要求
1. 基线文档的元信息表必须写明 `状态：已基线（Baseline）` 与版本号（如 v1.0）。
2. 实现阶段如需变更规格，**必须先提变更请求**：在 `10-change-requests.md` 中记录变更编号（CR-xx）、变更内容、影响范围、影响到的文档与代码，经人类批准后方可修改，并将相关文档版本递增。
3. 实现过程中发现规格缺陷时，Agent 应**停止实现并报告**，而不是自行"修正"规格。
4. 基线文档的修改只允许**追加变更记录**，不得静默覆盖历史内容。

### 禁止事项
- 禁止在写代码时顺手改规格以"让代码和文档对上"。
- 禁止删除或重写已被确认的章节。
- 禁止在未登记的变更下递增版本号。

### 验收检查
- [ ] 基线文档状态字段正确
- [ ] 存在 `10-change-requests.md`，所有规格变更有 CR-xx 编号
- [ ] 实现期 `specs/` 的改动均可在 CR 中追溯

## 6. P-05 · 分层架构原则（Layered Architecture）

### 声明
**必须采用分层架构，至少包含：表现层、应用服务层、领域层、基础设施/持久化层。** 依赖方向**严格单向向下**，禁止反向依赖与跨层穿梭。

### 具体要求
1. 四层职责边界：

   | 层 | 职责 | 禁止包含 |
   |---|---|---|
   | 表现层 Presentation | 接收 HTTP 请求、参数校验与格式转换、组装统一响应 `{code, message, data}` | 业务规则、SQL |
   | 应用服务层 Application Service | 用例编排、事务边界、调用领域对象与仓储 | HTTP 细节、SQL |
   | 领域层 Domain | 实体、值对象、领域服务、**Policy（借阅/罚款/预约规则）**、状态流转 | 框架依赖、数据库访问 |
   | 基础设施/持久化层 Infrastructure | ORM 模型、仓储实现、数据库连接、外部适配 | 业务规则 |

2. 依赖规则：表现层 → 应用服务层 → 领域层 ← 基础设施层（基础设施实现领域层定义的仓储接口）。
3. 领域层**不得 import** FastAPI / SQLAlchemy 等框架模块。
4. 业务规则（借阅数量、期限、罚款费率、超期判定、预约去重）**必须位于领域层的 Policy 或领域服务中**，不得散落在路由或仓储。
5. 分层结构对应 `00-project-brief.md` §9.1 差距项 **G-08**（基线逻辑集中在路由层），实现时必须消解。

### 禁止事项
- 禁止表现层直接访问数据库或 ORM 模型。
- 禁止领域层反向调用应用服务层或表现层。
- 禁止在仓储实现中编写业务判断。

### 验收检查
- [ ] 目录结构清晰体现四层（`backend/app/presentation|application|domain|infrastructure/` 或等价划分）
- [ ] 静态检查：领域层无框架 import
- [ ] 每条业务规则可在领域层定位到单一实现点

## 7. P-06 · MVC 原则

### 声明
**界面/表现层遵循 MVC：Controller 只负责接收请求与选择响应，Model 承载数据与领域行为，View 负责呈现。业务规则严禁写入 Controller。**

### 具体要求
1. Controller 允许做的事：**参数绑定与基础校验 → 调用一个应用服务方法 → 把结果映射为统一响应**。一个 Controller 方法体内不应出现 `if 超期`、`if 超额` 之类的业务判断。
2. Controller 方法应保持"薄"，原则上不超过一次服务调用 + 一次响应组装。
3. 本项目的 View 形态按已确认决策为 **REST API + Agent 对话**（`01-clarifying-questions.md` Q-27 建议默认），不另建 Web 前端；若后续新增界面，必须遵守同一约束。
4. 统一响应结构沿用基线 `{code, message, data}`，`code` 取值：`200` 成功 / `400` 业务错误 / `404` 资源不存在 / `500` 系统错误（与 `00-project-brief.md` §9 一致，不得另造错误码体系）。

### 禁止事项
- 禁止在 Controller 中编写业务规则、计算罚款、判断借阅配额。
- 禁止 Controller 直接操作 ORM 会话执行业务写操作。
- 禁止绕过统一响应结构返回裸字典或裸对象。

### 验收检查
- [ ] 每个 Controller 方法可映射到唯一的应用服务方法
- [ ] Controller 中无业务规则分支
- [ ] 所有端点返回 `{code, message, data}`

## 8. P-07 · 权限原则（Role Separation）

### 声明
**图书管理员、系统管理员、读者三者的权限必须严格区分，并在接口层强制校验。**

### 具体要求
1. 权限矩阵（依据 F-01 ~ F-03）：

   | 能力 | 读者 | 图书管理员 | 系统管理员 |
   |---|---|---|---|
   | 注册账号 | ✔ | — | — |
   | 检索图书 | ✔ | ✔ | ✔ |
   | 查询本人借阅信息 | ✔ | ✔（代查） | ✔ |
   | **办理借书 / 还书** | ✘ | **✔（唯一执行者）** | ✘ |
   | 预约图书 | ✔ | ✔（代办） | ✔ |
   | **办理借阅证** | ✘ | ✘ | **✔** |
   | 维护图书标题 / 馆藏副本 | ✘ | ✘ | **✔** |
   | 增删管理员、维护规则 | ✘ | ✘ | **✔** |

2. 第一阶段按 F-01 不做真实认证，但**必须实现轻量角色校验**：借还接口要求并校验 `librarian_id` 对应角色为 `librarian`；后台管理接口校验 `admin_id` 对应角色为 `admin`；读者接口校验 `user_id` 存在且角色为 `reader`。
3. 读者尝试借书必须被**明确拒绝**（返回业务错误，而非静默成功或降级为预约）。
4. 权限校验集中在一处（建议表现层的依赖/守卫或应用服务的统一前置校验），**不得在每个接口里各写一遍**。
5. 权限失败场景**必须有测试覆盖**（见 P-09）。

### 禁止事项
- 禁止"只要传了 ID 就通过"的无校验实现。
- 禁止让读者绕过管理员完成借还（与 F-02 冲突）。
- 禁止把权限判断写在 SQL 或仓储里。

### 验收检查
- [ ] 权限矩阵在 `04-business-rules.md` 中落盘并与本表一致
- [ ] 每个受限端点均有角色校验
- [ ] 存在"读者借书被拒""管理员越权访问后台接口被拒"的测试用例

## 9. P-08 · 业务规则集中原则（Centralized Policy）

### 声明
**借阅数量、借阅期限、超期判定、罚款计算、预约规则等，必须集中在 Policy 对象或领域服务中实现，禁止硬编码散落。**

### 具体要求
1. 规则集中点（建议落在领域层）：
   - `BorrowPolicy`：最大借阅数量、借阅期限（读者类型 × 借出物类型二维，类型维度暂 TBD(D-02)）、是否允许续借
   - `FineRule` / `FinePolicy`：各借出物类型费率（F-06）、超期天数口径（TBD(D-03) 封顶与免罚期）、罚款金额计算
   - `ReservationPolicy`：FIFO 排队（F-08）、同读者同标题去重（Q-32）、保留期与取消（TBD(D-05)）
   - `CardPolicy`：借阅证号生成规则（F-09）、一人一有效证（F-10）
2. 规则**参数化、可配置**：数值来自规则表/配置，不得写成魔法数字；新增读者类型或借出物类型时不应改动判断逻辑。
3. 每条规则必须在 `04-business-rules.md` 中有**唯一编号**（如 `BR-BORROW-01`），并在代码注释中回引该编号。
4. 禁止在代码里使用 `if reader_type == ...` 之类的类型分支链；应使用策略/查表。

### 禁止事项
- 禁止把费率、天数、数量写死在路由函数或 SQL 里（基线 `routes.py` 中 `timedelta(days=30)` 与 `0.5 元/天` 即为反例，对应差距项 G-04、G-05）。
- 禁止同一规则在不同模块出现多份实现。
- 禁止为"先跑通"临时硬编码而不留 TODO 追踪。

### 验收检查
- [ ] 规则类/策略对象可在领域层单一路径定位
- [ ] 代码中无业务魔法数字（或均带 `BR-` 编号注释）
- [ ] 修改规则参数无需改动业务判断代码

## 10. P-09 · 测试闭环原则（Test Closure）

### 声明
**核心用例必须有自动化测试。测试结果是用例"完成"的唯一判据——测试未通过的用例不得标记为已完成。**

### 具体要求
1. **必须覆盖的最小测试集**（对应 `00-project-brief.md` NFR-02）：
   | 场景 | 必须断言 |
   |---|---|
   | **借书成功** | 生成借阅记录、可借复本 -1、`due_date` 符合读者类型期限 |
   | **借书失败-超额** | 达到上限时拒绝并给出业务错误码 400 |
   | **借书失败-有超期** | 存在超期未还时拒绝（F-07） |
   | **还书成功** | 复本 +1、记录状态转为已归还 |
   | **还书-超期罚款** | 按借出物类型费率算出正确罚款金额（F-06） |
   | **预约成功与排队** | FIFO 顺序正确（F-08） |
   | **预约失败-重复预约** | 同读者同标题重复预约被拒（Q-32） |
   | **权限失败** | 读者借书被拒；管理员越权访问后台接口被拒（P-07） |
2. 采用 `pytest` + FastAPI `TestClient`（`01-clarifying-questions.md` Q-28 建议默认），测试使用独立临时数据库，不得污染 `library.db`。
3. 测试用例编号与用例编号对应（如 `test_UC03_borrow_success`），保持 NFR-03 可追溯性。
4. 每个业务规则（`BR-` 编号）至少有一个对应用例。
5. 测试失败时，Agent 应优先判断是**实现错误**还是**测试错误**，并在报告中说明，**不得通过删改断言使测试变绿**。

### 禁止事项
- 禁止只做手工 curl 验证即宣称完成（curl 记录作为补充验证，不替代自动化测试）。
- 禁止注释、跳过（`skip`）、删除失败用例来"修复"测试。
- 禁止测试依赖执行顺序或共享可变状态。

### 验收检查
- [ ] `pytest` 可一键运行且全绿
- [ ] 上表 8 类场景均有对应用例
- [ ] 测试与用例/规则编号可双向追溯

## 11. P-10 · Git 审查原则（Diff Review）

### 声明
**Agent 每次修改代码后，必须查看 `git diff` 并逐项说明改动，禁止"改完即走"。**

### 具体要求
1. 每次代码修改后执行 `git --no-pager diff`（必要时加 `--stat` 概览 + 逐文件细看），确认：
   - 改动是否超出本次任务范围（越界修改须回滚）；
   - 是否误删、误改既有逻辑；
   - 是否引入与基线文档（F-01~F-10）冲突的变更；
   - 是否夹带调试代码、临时文件、密钥或数据库文件。
2. 在回复中给出**改动摘要**：变更文件清单、每个文件的改动意图、是否存在需要人类注意的风险点。
3. 提交前再次核对：范围外文件应保持未修改状态（例如仅要求改 `specs/` 时，`backend/` 不得出现在 diff 中）。
4. 鼓励小步提交：一个用例/一条规则一次提交，便于审查与回滚。

### 禁止事项
- 禁止不看 diff 就直接宣称"已完成修改"。
- 禁止在 diff 中夹带与本次任务无关的重构、格式化、依赖升级。
- 禁止把 `library.db`、`__pycache__/`、`.pyc` 等产物提交进仓库。

### 验收检查
- [ ] 每次代码改动后已在回复中附上 diff 摘要
- [ ] diff 中无越界文件、无构建产物
- [ ] 提交粒度与任务项对应

## 12. P-11 · AI 使用记录原则（AI Usage Log）

### 声明
**每一次使用 Agent 生成内容，都必须记录到 `specs/19-ai-usage-log.md`。未记录即视为未发生，相关产出不纳入基线。**

### 具体要求
1. 记录时机：**每次 Agent 产出制品（规格/图/代码/测试）后立即追加一条**，不得批量补记。
2. 每条记录至少包含：

   | 字段 | 说明 |
   |---|---|
   | 序号 | 自增，如 `AI-001` |
   | 日期 | 生成日期 |
   | 任务 | 本次要求 Agent 做的事 |
   | 模型/Agent | 使用的模型或 Agent 名称 |
   | 产出物 | 新增/修改的文件清单 |
   | 人类审查 | ☐ 待审 / ☑ 已确认（确认人） |
   | 修改幅度 | 人类对 Agent 产出做了多少改动（原样采纳 / 小改 / 大改 / 重写） |
   | 备注 | 风险点、遗留问题 |

3. 若某次产出被人类**大改或重写**，必须在备注中说明原因，作为后续改进 Agent 提示词的依据。
4. 本宪章自身、以及每一份规格文档，都应在 `19-ai-usage-log.md` 中有对应记录。

### 禁止事项
- 禁止事后凭记忆补写日志。
- 禁止不记录"只改了一行"的小改动。
- 禁止由 Agent 在无人确认的情况下把日志条目标记为"已确认"。

### 验收检查
- [ ] `specs/19-ai-usage-log.md` 存在且记录连续无缺号
- [ ] 每条记录含产出物清单与审查状态
- [ ] 所有基线制品均可在日志中追溯到生成记录
